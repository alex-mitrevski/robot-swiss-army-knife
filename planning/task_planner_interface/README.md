# task_planner_interface

A Python-based package that exposes an interface (a Python package and a ROS 2 interface on top of that) for interacting with a logic-based knowledge base and a PDDL task planner.

The Python interface is adapted from [this repository](https://github.com/alex-mitrevski/task-planner/tree/master/task_planner).

## Dependencies

* [robot_swiss_knife_msgs](https://github.com/alex-mitrevski/robot-swiss-army-knife/tree/main/robot_swiss_knife_msgs)
* [kb_interface](https://github.com/alex-mitrevski/robot-swiss-army-knife/tree/main/knowledge/kb_interface)

## Usage instructions

There are two ways to use the component:
* Over ROS 2 (this is particularly useful for C++-based components)
* As an ordinary Python component

### Interaction over ROS

The component includes a node that exposes services for interacting with a knowledge base and a task planner; in other words, this includes both services that are provided in the [kb_interface package](https://github.com/alex-mitrevski/robot-swiss-army-knife/tree/main/knowledge/kb_interface) as well as additional services for adding / removing planning goals and invoking the task planner.

After building this package, the node can be started as follows:
```
ros2 launch task_planner_interface task_planner_interface.launch.py
```

The component exposes four services and one action:
* A service for retrieving fluent assertions. The interface used by this service is of type [robot_swiss_knife_msgs/srv/GetFluentAssertions](https://github.com/alex-mitrevski/robot-swiss-army-knife/blob/main/robot_swiss_knife_msgs/srv/GetFluentAssertions.srv). If the name in the request is left empty, all assertions will be retrieved from the knowledge base.
* A service for retrieving planning goals. The interface used by this service is also of type [robot_swiss_knife_msgs/srv/GetFluentAssertions](https://github.com/alex-mitrevski/robot-swiss-army-knife/blob/main/robot_swiss_knife_msgs/srv/GetFluentAssertions.srv) (but the request is ignored).
* A service for updating the knowledge base (inserting or removing assertions). The interface used by this service is of type [robot_swiss_knife_msgs/srv/UpdateKB](https://github.com/alex-mitrevski/robot-swiss-army-knife/blob/main/robot_swiss_knife_msgs/srv/UpdateKB.srv).
* A service for updating the planning goals (inserting or removing goals). The interface used by this service is also of type [robot_swiss_knife_msgs/srv/UpdateKB](https://github.com/alex-mitrevski/robot-swiss-army-knife/blob/main/robot_swiss_knife_msgs/srv/UpdateKB.srv).
* An action for generating a task plan with the current knowledge state and with the current goals. The interface used by the action is of type [robot_swiss_knife_msgs/action/GetTaskPlan](https://github.com/alex-mitrevski/robot-swiss-army-knife/blob/main/robot_swiss_knife_msgs/action/GetTaskPlan.action).

The names of the services (`get_fluent_assertions`, `get_goals`, `update_kb`, and `update_goals` by default) as well as the action name (`plan` by default) can be specified in the launch file (all of these exist in the `/planner` namespace by default). The following parameters can / should also be specified through the launch file:
* Four parameters that should be set in [`config/planner_config.yaml`](https://github.com/alex-mitrevski/robot-swiss-army-knife/blob/main/planning/task_planner_interface/config/planner_config.yaml):
    * `planner_name`: Name of the planner (default `lama`). The allowed planner names are specified as constants in the `PlannerNames` class in the [`task_planner_interfaces.planner_interfaces`](https://github.com/alex-mitrevski/robot-swiss-army-knife/blob/main/planning/task_planner_interface/task_planner_interface/planner_interface) package.
    * `domain_file`: The name of the PDDL domain file to be used by the planner. The package includes two domain files under `config/task_domains` (`service_robot_domain.pddl` and `hospital_transportation.pddl`), so this value could be one of those (or a custom domain, but then the path should be adjusted in the launch file).
    * `planner_cmd`: The planner command to run when invoking the planner (this is planner-specific and requires the absolute path to the executable to be specified, as can be seen in the example config file)
    * `plan_file_path`: Path where any temporary files generated by the task planner should be stored (default `.`)
* `kb_db_name`: Name of the database used for knowledge base storage (default `robot_store`)

An example of a Python-based ROS 2 node for interacting with the knowledge base can be found in [`planner_ros_test.py`](https://github.com/alex-mitrevski/robot-swiss-army-knife/blob/main/planning/task_planner_interface/test/planner_ros_test.py) in the `test` directory.

### Interaction over Python

Python components can also interact with the planner interface through an instance of a planner-specific class from the `task_planner_interface.planner_interfaces` package (note that, currently, only the [LAMA planner](https://www.fast-downward.org/latest/) is supported).

Examples of interacting with the planning interface over Python can be found in [`planner_python_test.py`](https://github.com/alex-mitrevski/robot-swiss-army-knife/blob/main/planning/task_planner_interface/test/planner_python_test.py) in the `test` directory.

Note, however, that the `domain_file` variable in the config file should include the absolute path to the domain file when the planner is used this way (unless you want to introduce a dependency on `ament_index_python.`).
